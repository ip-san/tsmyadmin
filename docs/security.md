# セキュリティモデル

*English: [docs/en/security.md](en/security.md)*

## 前提

- tsmyadmin は **DB の資格情報を持つ利用者が、その権限の範囲で任意の SQL を実行するためのツール** です。phpMyAdmin と同じく、アプリ側で SQL を制限することは目的ではありません。守るのは「資格情報を持たない者が使えないこと」「意図しない接続先へ踏み台にされないこと」「値がロスレスかつ安全に往復すること」です
- 到達性はネットワーク側で絞ってください（VPN / 社内ネットワーク / IP 制限 / SSO プロキシ）。インターネットに直接公開する用途は想定していません

## 認証とセッション

- 保存する行はそれぞれ自分の行に結び付けて暗号化します（AES-GCM の追加認証データに `テーブル名:行 ID` を入れる）。ファイルに書き込めるが復号はできない者が、他人の行の暗号文を自分の行に上書きして「自分のセッションを他人の資格情報で動かす」ことを防ぎます。読めない行はその都度破棄します
- 資格情報はサーバー側にだけ保持され、ブラウザには **署名付きセッション ID の Cookie**（`HttpOnly`, `SameSite=Strict`, 本番では `Secure`）しか渡りません。本番既定の `SESSION_STORE=sqlite` では、資格情報は `SESSION_SECRET` から HKDF で導出した鍵による AES-256-GCM で暗号化して保存します（ファイルだけ持ち出されても復号できません。`SESSION_SECRET` は環境変数として厳重に管理してください）
- セッションは無操作 `SESSION_TTL_MINUTES` で失効し、ログアウト / 失効時に DB 接続プールを閉じます
- パスワードは API のレスポンス（`GET /api/session`）、ログ、アカウント操作のプレビュー / 実行結果、DB エラーメッセージのいずれにも含めません（マスク `****`）。SQL コンソールに直接入力した `IDENTIFIED BY '…'` / `PASSWORD '…'` / `SET PASSWORD … = '…'` も監査ログに書く前にマスクします（コメントを除去してから照合し、`IDENTIFIED` / `PASSWORD` を含む文では認証キーワード以降の最初の引用符から最後の引用符までを 1 つのマスクにします — `PREPARE` / `EXECUTE` / `format()` に文字列として渡した文や `''` の入れ子でも断片が残りません。`SOURCE_PASSWORD` などの `*_PASSWORD`、接続文字列中の `password=…`、`AS 0x…` のハッシュも対象です。要約は再実行用ではないためコメントは失われます）
- 想定外の内部エラーはクライアントに `INTERNAL` とだけ返し、メッセージやスタックはサーバーログにのみ残します
- リクエスト本文の上限: `/api/session` 64 KB、SQL 実行 16 MB、インポート `IMPORT_MAX_BYTES`（64 MB）、その他の JSON 1 MB。超過は `413 PAYLOAD_TOO_LARGE`（インポートはファイルが 64 MB を超えた場合も、マルチパート本文が 65 MB を超えた場合も同じ）

## 2 要素認証（TOTP・パスキー）

- ログインした DB アカウントごとに、認証アプリのワンタイムコードを追加できます（「セキュリティ」タブ）。秘密鍵と回復用コードのハッシュは、資格情報と同じ鍵で暗号化してセッションストアに保存します（アカウントごとに 1 行。保存済みクエリの件数上限とは無関係です）。したがって `SESSION_STORE=sqlite` か `redis` が必要です
- **何を守るか**: この製品では DB の認証情報がそのまま利用者の身元です。したがってパスワードを知っている者は、先に自分で登録してしまうこともできます。2 要素認証が効くのは**登録した後にパスワードが漏れた場合**（使い回し、覗き見、流出した一覧など）です。この「登録前の窓」を閉じるのが `TSMYADMIN_REQUIRE_2FA=1` で、未登録のアカウントは登録を終えるまで何もできません
- 一度受け付けたコードは、その 30 秒の間でも二度は使えません（受理したステップを記録しています）。回復用コードは 1 つにつき 1 回です。コードの試行は、ログイン失敗と同じ IP 単位の枠で数えます
- 解除には認証アプリの現在のコードが必要です。登録済みの鍵を別の鍵に置き換える操作も同様です（そうでないと、解除の確認を迂回できてしまいます）
- **端末を失ったとき**: 回復用コードを使うか、そのアカウントのパスワードを変えられるアカウント（MySQL は `CREATE USER`、MySQL 8 はさらに `SYSTEM_USER`。PostgreSQL はスーパーユーザーか、対象を管理できる `CREATEROLE`）で「ユーザー」タブから解除します。DB の権限で乗っ取れる相手にしか効かないので、守りは下がりません。自分自身の分はここからは解除できません（コードが要るセキュリティタブを通す）。解除は `second_factor.reset` としてログに残ります。MySQL 8 では、対象が `SYSTEM_USER` を持つかどうかを誰からでも確かめられるわけではないため、`SYSTEM_USER` を持たない運用者には（相手が持っていなくても）解除を出しません（安全側の判断）。解除できるのは同じ接続先（ホスト名とポート）で登録したアカウントです。最後の手段として、保存を直接消すこともできます（`sqlite` なら `DELETE FROM second_factor;`、`redis` なら `DEL <prefix>:2fa:*`。全員分が消えます）。`SESSION_SECRET` を入れ替えた場合は、全員の登録が消えます（読めない行を残して締め出さないため）
- **パスキー（WebAuthn）**: `TSMYADMIN_PASSKEY_ORIGIN` を設定すると、認証アプリの代わりに（または並べて）パスキーを 2 要素目にできます。パスワードの代わりにはなりません（DB への接続にパスワードそのものが要るため）。検証は `@simplewebauthn/server` に任せ、登録元の origin とホスト名、署名、サーバーが渡したチャレンジを確かめます。チャレンジは 2 分で失効し、1 回しか使えません。ログイン時のチャレンジはパスワードが通った後にだけ渡し、そのアカウントに結び付けます（パスワードを知らない者には、誰がパスキーを持っているかも見えません）。署名カウンタを持つ認証器では、カウンタが進まない応答（複製された認証器など）を拒否します。パスキーはホスト名に結び付くため、配備のドメインを変えると登録済みのものは使えなくなります（回復用コードか、運用者による解除で戻します）
- 方法の追加・削除・全解除には、今ある方法での本人確認（認証アプリの現在のコードか、登録済みのパスキー）が要ります。回復用コードは本人確認に使えません（ログインのためのものなので）。最後の方法を外すと、回復用コードも含めて 2 要素認証が解除されます
- 登録時の QR コードはサーバー内で作り、画面はその白黒の配列を図形として描くだけです。秘密鍵を外部の QR 生成サービスに送ることはありません
- パスワードマネージャーの自動入力に任せられるよう、コード欄は `autocomplete="one-time-code"` です。コードは保存も記録もしません

## 接続先の制限（SSRF / 踏み台対策）

ログイン画面で指定できる DB ホストは `TSMYADMIN_ALLOWED_HOSTS` に列挙したものだけです。既定はローカルのみ。`*` は開発用途でのみ使ってください。不許可のホスト / ポートへの接続は DB に触れる前に `403 HOST_NOT_ALLOWED` で拒否され、`login.host_not_allowed` として記録されます。

エントリは `host[:port]` です（`db.internal:5432`、`[::1]:3306`、`*.rds.amazonaws.com:5432`）。**本番ではポートまで指定してください**: ポートを省略したエントリはそのホストの全ポートを許可するため、未認証のログイン要求が「接続できた / 認証に失敗した」の違いから、許可ホスト上で待ち受けている他サービスを探るポートスキャンの踏み台になり得ます。本番（`NODE_ENV=production`）では起動時にポート省略のエントリがあると `config.allowlist_without_port` を警告します。接続先プリセット（`TSMYADMIN_SERVERS`）はそのプリセットの `host:port` だけを自動で許可します。

### Docker コンテナの自動検出（開発用）

`TSMYADMIN_DOCKER_DISCOVERY=1` は、Docker ソケットを読み、検出したコンテナの**公開 `ホスト:ポート` だけ**を許可リストに加えます（ポート単位で、別のポートや別のホストは広げません）。ソケットを読めることはホストの root と同じ強さなので、**開発機の手元だけ**で使い、`NODE_ENV=production` では起動時に拒否します。コードが発行するのは `GET /containers/json` と `GET /containers/<id>/json` だけで、コンテナの環境変数からは `MYSQL_DATABASE` / `MARIADB_DATABASE` / `POSTGRES_DB` しか取り出しません（既定ではパスワードは読まず、返さず、記録しません）。`TSMYADMIN_DOCKER_LOGIN=1` を明示したときだけ、コンテナの起動時の資格情報（`MYSQL_ROOT_PASSWORD` / `POSTGRES_PASSWORD` など）を API のプロセスの中に読み、パスワードなしの 1 クリックで入れるようにします。そのパスワードはブラウザに返さず、ログにも保存にも出さず、検出したコンテナ自身の `ホスト:ポート` にだけ使います。ただし、**このツールに届く人は誰でも、パスワードなしでそれらの DB に入れます**。`127.0.0.1` にだけ公開し、共有マシンや公開ネットワークでは使わないでください（`NODE_ENV=production` では検出ごと拒否します）。ソケットを `:ro` でマウントしても Docker API への書き込みは防げないので、守りは「渡さないこと」です。使い方は [deployment.md](deployment.md#docker-で開発用に使うコンテナの自動検出)。

## ブルートフォース対策

`POST /api/session` はクライアント IP + ユーザー名ごとに `LOGIN_RATE_LIMIT` 回 / `LOGIN_RATE_WINDOW_SECONDS` 秒に制限され、超過は `429 RATE_LIMITED`（`Retry-After` 付き）になります。

クライアント IP は既定ではソケットのアドレスです。`TRUST_PROXY=1` では `X-Forwarded-For` の**末尾**（信頼するプロキシが追記した要素。先頭はクライアントが自由に書けます）を使い、`TRUST_PROXY=cloudflare` では `CF-Connecting-IP` を優先して、それが無ければ `1` と同じ動きに戻ります。`X-Real-IP` 等のヘッダーはどの設定でも信用しません。
成功時にカウンタはリセットされます。加えてユーザー名を変えながらの試行を防ぐため、IP 単位でも **失敗** `LOGIN_RATE_LIMIT × 3` 回 / 同じウィンドウで制限します（成功したログインは数えないので、共有 NAT 配下の正常な利用者を締め出しません）。許可リストにないホストへの試行もこの IP 側に数えます（`403` と `401` の差でホストの存在を探れるため）。その結果、古い接続先プリセットが残っていると、共有 NAT の内側では他の利用者のログインまで `429` になり得ます。

セッション Cookie の `Max-Age` は認証済みリクエストのたびに再発行され、サーバー側のスライド式 TTL と同期します。

## 接続数の上限（DB 側の `max_connections` 保護）

ログインごとにセッション（= 接続プール）が作られ、それに加えて実行中のクエリのキャンセル 1 回につき専用接続を 1 本開きます（同じ実行への同時キャンセルは 1 本を共有。プールの接続数が上限なので、セッションあたり最大 +4 本）。同じ DB アカウントで保持するセッションは `SESSION_MAX_PER_IDENTITY`（既定 10）までとし、超えた分は最後に使われてから最も時間が経ったもの（LRU）から閉じます。ログアウトせずに再ログインしたブラウザの以前のセッションも閉じます。必要な `max_connections` の見積もり式は [deployment.md](deployment.md) の「サイズと制限」にまとめてあります。

## SQL コンソールの行数上限について

「最大行数」は誤操作（`SELECT * FROM 巨大テーブル`）で API のメモリを使い切らないための上限で、アカウント自身に対する制限ではありません。MySQL / MariaDB は `sql_select_limit` で、PostgreSQL は派生テーブルの `LIMIT` で実現しており、文自身の `LIMIT` はそのまま尊重されます（上限を超える `LIMIT` を書いた文は派生テーブルで包み直します）。スクリプト内で `SET SESSION sql_select_limit` を実行しても、その文の後で上限を再適用します。例外: 派生テーブルに包めない文（`FOR UPDATE` / `LOCK IN SHARE MODE` / `INTO`、MySQL がラッパーを拒否する `SQL_CALC_FOUND_ROWS` など）に大きな `LIMIT` を書いた場合はその `LIMIT` がそのまま効きます。

## エクスポートの `DEFINER` 句

SQL エクスポートの「`DEFINER` 句を除く」は、復元したビュー・ルーチン・トリガーの定義者を復元するアカウントに変えます。`SQL SECURITY DEFINER` のオブジェクトはその権限で実行されるようになるため、元の定義者より強い権限で復元する場合は内容を確認してください（mysqldump の `--skip-definer` と同じトレードオフ）。

## ブラウザ側に残るデータ

サーバー側に資格情報を閉じ込める一方で、利便性のために次のものが**そのブラウザの `localStorage`** に残ります。いずれもマスクや暗号化はしていません。

| 保存されるもの | 内容 |
|---|---|
| SQL の履歴 | 直近 100 件の実行文（接続先ごと）。`CREATE USER … IDENTIFIED BY 'x'` のようにパスワードを含む文も**そのまま**残ります（監査ログでは `****` にマスクされます） |
| 保存済みクエリ | 利用者が名前を付けて保存した SQL。`SESSION_STORE=memory` のときだけここに残ります（本番既定の `sqlite` ではサーバー側に資格情報と同じ鍵で暗号化して保存され、ブラウザには残りません） |
| 最後のログイン先 | 方言・ホスト・ポート・ユーザー名・データベース（**パスワードは保存しません**） |
| 表示設定 | 表示言語、テーマ、サイドバーの開閉、1 ページの行数など |

共有端末では、離席前に SQL タブの「履歴をクリア」を実行し、ログアウトしてください。セッションを永続化していない構成では履歴はブラウザの `localStorage` にだけあり、サーバーには送られないため、tsmyadmin 側から消すことはできません。永続化している構成では履歴はアカウントに暗号化して保存され、「履歴をクリア」がサーバー側の記録も消します。

## `SESSION_SECRET` 漏えい時の対応

1. 新しい値（`openssl rand -hex 32`）を設定して再起動します。起動時に鍵の指紋が変わったことを検出して保存済みセッションの行をすべて削除し（ログ `session_store.reset`）、Cookie の署名も無効になるので、全員が再ログインになります（保存済みクエリ・エクスポートのテンプレート・2 要素認証の登録も同時に消えます）（`SESSION_STORE=memory` でも署名鍵のため手順 1 は必要です）
2. `data/sessions.sqlite`（`-wal` / `-shm` 含む）も同時に流出した可能性がある場合は、その中の資格情報が復号され得るため、露出期間中に `login.ok` に記録された `user@host` の DB パスワードを変更してください
3. ログには生のセッション ID は書かれません（`sessionId` はハッシュの先頭 16 桁）。それでもログはシークレットと同じ水準でアクセス制御してください

## CSRF / XSS

- `SameSite=Strict` Cookie に加え、フォーム（マルチパート）POST は `Origin` 検証（`hono/csrf`）で保護します。JSON API はブラウザのクロスオリジン制約（CORS 未許可）により外部サイトから呼べません
- `Content-Security-Policy: default-src 'self'; script-src 'self'; frame-ancestors 'none'` など（`apps/api/src/app.ts` の `contentSecurityPolicy`）。インライン script は許可しません。CodeMirror の都合で `style-src 'unsafe-inline'` のみ許可しています
- 値の描画はすべて React 経由（`dangerouslySetInnerHTML` 不使用）
- 列の表示変換（構造タブ）のリンクは http / https だけで、値は URL エンコードしてテンプレートに差し込みます（値でリンク先のホストや `javascript:` を作れない。テンプレートの登録時と描画時の両方で検査）。画像はセルのバイト列から PNG / JPEG / GIF / WebP と判別できたものだけを `data:` URL で表示し、SVG は扱いません。外部の画像 URL は、環境変数 `TSMYADMIN_IMAGE_HOSTS` に書いたホストだけが CSP の `img-src` に加わり（書式は起動時に検証し、CSP の記述を足せない形に限ります）、そのホスト以外は読み込まれずリンクになります。ホストを書くと、画像を開いた閲覧者の IP アドレスなどがそのホストに伝わります。「HTML を整形して表示」の変換は、値を不活性な文書として解析し、許可リストの要素だけを新しく作って描きます（属性は http(s) の `href` だけ。`script`・`style`・`iframe`・イベント属性・`javascript:` と `data:` のリンクは捨てる。文字列として HTML に差し込むことはしません）
- 変数ページの「マニュアル」リンクは、公式マニュアルの固定のホスト（`dev.mysql.com`、`mariadb.com`、`www.postgresql.org`）だけを指し、変数名は英数字・`_`・`.` に限って（それ以外は作らない）URL に入れます。新しいタブで `noopener noreferrer` を付けて開くので、外部へ渡るのは変数名だけです

## SQL の組み立て

- 識別子は必ずクォート（`quoteIdent`）、値は必ずプレースホルダ。文字列補間で SQL を組み立てられる場所はアダプター内の限られたビルダーだけで、`bun run check:sql-safety` が CI で強制します
- DDL・アカウント操作は生成 SQL をプレビューし、利用者の明示的な確認後にのみ実行します
- 行の更新 / 削除はトランザクション内で「影響行数 = 1」を検証し、違えばロールバックします

## 監査

構造化ログ（`LOG_FORMAT=json`）に `login.ok` / `login.failed` / `login.host_not_allowed` / `login.rate_limited` / `logout` とリクエスト ID 付きのアクセスログが出ます。変更系の呼び出しはアダプター境界の監査ログ（`event: audit`）に、誰が・どの DB に・何を（行の値は含まない。SQL コンソールの文は先頭 500 文字を記録するため値を含み得る。インポートは `<import>` と実行スクリプトの文字数だけを記録する）・成功したかが記録されます。詳細は `docs/operations.md`。

## サプライチェーン

- GitHub Actions はコミット SHA でピン留めし（`.github/workflows/ci.yml`、タグはコメントで併記）、Dependabot（`.github/dependabot.yml`）が Actions と `bun.lock` の依存について月次で更新 PR を出します
- 依存は `bun.lock` で固定し、本番イメージは `bun install --production --ignore-scripts` で postinstall スクリプトを実行しません

## 既知の制限

- セッションストアは SQLite ファイルのため、複数レプリカで共有できません（スティッキーセッションが必要）
- MySQL の `DELIMITER xx` は行頭に単独で書かれた場合だけ解釈します（mysql クライアント互換）
- DB 側のユーザー権限が唯一のアクセス制御です。tsmyadmin に独自のロールはありません。ユーザーグループはタブを隠すだけで、隠したタブの API はアカウント自身の権限の範囲でそのまま使えます（グループの変更はメンバー全員を管理できるアカウントに限り、メンバー自身が外すことはできません）。権限不足は `PERMISSION_DENIED`（403）として区別して表示します（`docs/operations.md` 参照）

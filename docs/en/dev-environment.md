# Development features: what was built, and what was set aside

*日本語版: [docs/dev-environment.md](../dev-environment.md)*

tsmyadmin's core for development is opening the MySQL / PostgreSQL running in your local Docker in the browser without writing their addresses down ([deployment.md](deployment.md#using-it-for-development-with-docker-container-discovery)). This page records what was added on top of that for development, what was considered and set aside, and what comes next, with the reasons. How to start it is in the README ("すぐ使う（開発環境）", the quick start for development), usage is in [user-guide.md](user-guide.md); [deployment.md](deployment.md) is the only source for environment variables.

## How this differs from phpMyAdmin

phpMyAdmin is for MySQL / MariaDB only, and you name the server in `config.inc.php` or an environment variable such as `PMA_HOST`. It does have a server dropdown on the login screen (with several servers configured), but that list is a fixed one you wrote. It has no discovery of Docker containers, and no PostgreSQL support. What tsmyadmin does differently is not the dropdown but that **the list fills itself from Docker without your writing it**, and that **PostgreSQL is on the same screen**.

## What was built

| Feature | Where | In short |
|---|---|---|
| **Statements as they run** | Server → Monitor | Streams the SQL the application under development is running now. MySQL / MariaDB: the general log (a table), newest first. PostgreSQL: the statements whose call count grew in `pg_stat_statements`, per read. This tool's own statements are left out. The MySQL general log can be turned on after you review the SQL |
| **Snapshots** | Database → Snapshots | Saves the database as it is (structure, data, views, routines, triggers) so that after trying a migration or a seed you can put it back. A snapshot is the existing SQL export and a restore runs that SQL, the same on both dialects. Before a restore you review the SQL that drops the tables and views made since. PostgreSQL does it in one transaction. Held in memory (gone when it restarts, and 24 hours after being taken), per account |
| **Snapshot vs. schema diff** | Database → Snapshots → "Compare with now" | Compares a snapshot taken before a migration with the database now: the tables and views added, removed, and whose definition changed, each with a line diff of its CREATE statements. The definitions are kept with the snapshot, as its dump read them. Row data, `AUTO_INCREMENT=` and sequence positions are not compared. Only the account that took the snapshot can compare it |
| **One-click login** | Login screen | With `TSMYADMIN_DOCKER_LOGIN=1` (off by default), reads a container's login from its environment (`MYSQL_ROOT_PASSWORD`, `POSTGRES_PASSWORD`, …) inside the API process only and signs in without a password. Never sent to the browser, logged or stored. Anyone who can reach the tool can then get in, so publish it on `127.0.0.1` only |
| **Connection details for your application** | Login screen | When a discovered container is chosen, shows for each place the application may run (on the host, in a container of the same compose project, in a container on another network) the address (`127.0.0.1:13306`, `mysql:3306`, `host.docker.internal:13306`), a `DATABASE_URL` and `.env` lines (generic and Laravel), each with a copy button. The user name is `MYSQL_USER` / `POSTGRES_USER` (else `root` / `postgres`), the database the one discovery read. No password is read for it (and with `TSMYADMIN_DOCKER_LOGIN` none is returned); it is written as `<password>` |
| **Lock waits and connections** | Server → Processes | Finds the usual cause of an application that "hangs": a transaction left open. Each connection waiting for a lock is shown with the one holding it (for the holder, how long its transaction has been open and the statement it runs or ran last), and the holder can be ended through a confirmation. The connection count is compared with `max_connections`, with a warning above 80%. MySQL 8: `performance_schema`; MariaDB: `INNODB_LOCK_WAITS`; PostgreSQL: `pg_blocking_pids` |
| **Why a database is missing** | Login screen | Shows the database containers left off the list (stopped, port not published), why Docker cannot be read, and listed ports this process cannot reach, each with how to fix it |
| **Why a login failed (development only)** | Login screen | Tells apart the account and source address MySQL refused, its host restriction, PostgreSQL's `pg_hba.conf`, a wrong password, a port nothing listens on, and a host that cannot be reached or does not resolve, and says how to fix each. Production stays generic so as not to give out the source address |
| **Waiting for a container to start** | Login screen | While discovery is on, the server list is re-read every 5 s, so containers started or stopped later appear and leave without reopening the screen. The selected server and what was typed stay; when the selected container leaves, it stays selected, the form says it has left the list and holds back Connect (once it is back you connect as you are). A container whose healthcheck says `starting` is kept off the list and reported in the diagnosis as "starting (not ready yet)"; it joins the list once ready. Changes are announced through `aria-live` |

## Considered and set aside

- **An MCP server (on hold)**: for a client that has Bash, such as Claude Code, `docker exec … psql` and reading the migration files cover most of it. The real advantages of MCP are two: it can *enforce* "read-only" in the implementation (with Bash, allowing `docker exec` allows a DROP after it), and it works in clients without Bash (Claude Desktop, say). Both can wait until they are needed. A cheaper way is to write the connection commands in CLAUDE.md or a Skill.
- **Making zero-click login the development default**: it stays off even for `bun run dev` and `docker-compose.dev.yml`. Anyone who can reach the tool could then open the databases without a password, so it is an explicit choice (`docker-compose.dev.yml` has the line to turn it on, commented out).
- **Persisting snapshots**: they are kept in memory so as not to add an environment variable or put data on disk in the clear. They are lost on restart, and 24 hours after being taken (so that the ones of an account that never comes back do not keep filling the total shared by every account, where nobody can remove them). If needed, saving to disk can be added as a separate choice.
- **A real-time PostgreSQL stream**: `pg_stat_statements` is aggregated, normalised statements rather than a timeline of executions, and turning it on needs `shared_preload_libraries` and a restart (tsmyadmin issues only GET requests to Docker, so it cannot do that for you). So it shows the growth in call counts per read, and when the extension is unavailable it gives the steps to enable it in Docker.

## Next candidates

The five this section used to list (why a login failed, copying the connection info, lock waits, waiting for a container to start, snapshots with a schema diff) have all been built (see the table above). New candidates will be added here, in order of how much they help.

## Known limits

- **Initial JS budget**: about 160 kB of the 170 kB is used (`bun run size`). At 159.9 kB of 160 kB the budget was raised to 170 kB rather than trimmed. Where it goes (initial JS, minified): react-dom 33%, zod 17%, the language file 13%, TanStack Router and Query about 18%, the shared schemas about 7%. **zod cannot leave the first paint** (the route definitions validate their search parameters with it, and `readPreference` takes a zod schema, both on the first-paint path). Only the strings are a lever: loading each screen's strings with the screen could save up to about 20 kB, but it touches all 208 files that read `locale.` (53 of them capture a section at module level), and a section that is missed shows only at run time, as `undefined` on the screen that needs it, not in the types. Not worth it at this size: start from here when the budget is next exceeded.
- **A real PostgreSQL test**: the test compose has no `pg_stat_statements`, so the PostgreSQL path of "statements as they run" has been checked only in a throwaway container with the extension. Putting it in CI needs a change to the compose command and the fixtures (and a `db:reset`).
- **Only a container with a healthcheck can be told to be starting.** One without a healthcheck is listed as soon as it starts, even while the database does not accept connections yet (a Docker published port accepts connections before the process inside listens, so reaching it over TCP cannot tell). A login in that window fails to connect.
- **Leaving out "its own statements" is per connection** on MySQL: a second tsmyadmin session on the same server shows up as application traffic.

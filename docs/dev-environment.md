# 開発環境向けの機能: 何を作り、何を見送ったか

tsmyadmin は、手元の Docker で動いている MySQL / PostgreSQL を、接続先を書かずにブラウザで開けることを軸にしています（[deployment.md](deployment.md#docker-で開発用に使うコンテナの自動検出)）。このページは、その上に足した開発向けの機能と、検討して見送ったもの、次の候補を、判断の理由つきで残します。起動の手順は README の「すぐ使う（開発環境）」、使い方の詳細は [user-guide.md](user-guide.md)、環境変数は [deployment.md](deployment.md) が唯一の正です。

## 本家の phpMyAdmin との違い

本家は MySQL / MariaDB 専用で、接続先は `config.inc.php` や `PMA_HOST` などの環境変数で指定します。ログイン画面に接続先のドロップダウンを出す機能（複数サーバーの設定）はありますが、一覧は設定に書いた固定のものです。Docker のコンテナを検出して一覧を作る機能はなく、PostgreSQL にも対応していません。tsmyadmin が違うのは、ドロップダウンがあることではなく、**一覧を書かなくても Docker から自動で埋まること**と、**PostgreSQL も同じ画面に出ること**です。

## 作ったもの

| 機能 | 場所 | 要点 |
|---|---|---|
| **実行された文（リアルタイム）** | サーバー → モニター | 開発中のアプリが今実行している SQL を流す。MySQL / MariaDB は一般ログ（テーブル）を新しい順に、PostgreSQL は `pg_stat_statements` の回数の増加を読み取りごとに示す。tsmyadmin 自身の文は除く。MySQL の一般ログは、SQL を確認してから有効にできる |
| **スナップショット** | データベース → スナップショット | 今の状態（構造・データ・ビュー・ルーチン・トリガー）を保存し、マイグレーションやシードを試したあとで戻す。保存は既存の SQL エクスポート、復元はその SQL の実行で、両方言で同じ仕組み。復元の前に、保存のあとに作ったテーブル・ビューを削除する SQL を確認する。PostgreSQL は 1 つのトランザクション。メモリ保管（再起動で消える。取ってから 24 時間でも消える）で、アカウントごとに分ける |
| **ワンクリック ログイン** | ログイン画面 | `TSMYADMIN_DOCKER_LOGIN=1`（既定オフ）で、コンテナの環境変数（`MYSQL_ROOT_PASSWORD` / `POSTGRES_PASSWORD` など）の資格情報を API のプロセスの中だけで読み、パスワードなしで入る。ブラウザには返さず、ログにも保存にも出さない。届く人は誰でも入れるので `127.0.0.1` にだけ公開する |
| **アプリからつなぐ接続情報のコピー** | ログイン画面 | 検出したコンテナを選ぶと、アプリが動く場所（ホスト・同じ compose のコンテナ・別のネットワークのコンテナ）ごとに、アドレス（`127.0.0.1:13306`・`mysql:3306`・`host.docker.internal:13306`）、`DATABASE_URL`、`.env` の行（汎用と Laravel）を出し、コピーできる。ユーザー名は `MYSQL_USER` / `POSTGRES_USER`（なければ `root` / `postgres`）、データベース名は検出が読んだもの。パスワードは読まず（`TSMYADMIN_DOCKER_LOGIN` のときも返さない）、`<password>` と書く |
| **ロック待ちと接続数** | サーバー → プロセス | アプリが「固まった」ときによくある原因の、開いたままのトランザクションを見つける。待っている接続と待たせている接続を 1 行に並べ（待たせている側は、トランザクションの経過時間と、実行中か最後に実行した文）、待たせている側を確認ダイアログから終了できる。接続数を `max_connections` と比べ、80% を超えると警告する。MySQL 8 は `performance_schema`、MariaDB は `INNODB_LOCK_WAITS`、PostgreSQL は `pg_blocking_pids` |
| **見つからない理由の診断** | ログイン画面 | 一覧に出ない DB コンテナ（停止中・ポート未公開）、Docker を読めない理由、一覧にあっても API から届かないポートを、直し方つきで示す |
| **ログイン失敗の理由（開発時のみ）** | ログイン画面 | MySQL が拒否したアカウントと接続元のアドレス、ホスト制限、PostgreSQL の `pg_hba.conf`、パスワード違い、待ち受けていないポート、届かない・引けないホストを区別して、直し方を出す。本番は接続元のアドレスを漏らさないよう汎用のまま |
| **コンテナの起動を待つ** | ログイン画面 | 検出がオンの間、接続先の一覧を 5 秒ごとに取り直し、後から起動・停止したコンテナを開き直さずに反映する。選んでいる接続先と入力は変えず、選んでいるコンテナが消えたら、選んだまま「一覧から消えました」と示して「接続する」を止める（戻れば、そのまま接続できる）。ヘルスチェックが `starting` のコンテナは一覧に出さず、診断に「起動中（まだ準備ができていません）」と出し、準備ができたら一覧に加わる。変化は `aria-live` で読み上げる |

## 判断して見送ったもの

- **MCP サーバー化（保留）**: Claude Code のように Bash を使えるクライアントなら、`docker exec … psql` やマイグレーション ファイルの読み取りで、大半は代替できます。MCP の実質的な利点は、「読み取りだけ」を実装で強制できること（Bash では `docker exec` を許可した時点で、その先の DROP も打てる）と、Bash のないクライアント（Claude Desktop など）で使えることの 2 つです。どちらも必要になってから作れば足ります。コストを抑えるなら、接続コマンドを CLAUDE.md や Skill に書いておく方法があります。
- **ゼロクリック ログインを開発の既定にすること**: `bun run dev` や `docker-compose.dev.yml` でもオフのままです。届く人は誰でもパスワードなしで DB に入れる状態が既定になるため、明示的にオンにする設計にしました（`docker-compose.dev.yml` にはオンにする行をコメントで置いてあります）。
- **スナップショットの永続化**: メモリ保管にしたのは、環境変数を増やさず、データを平文でディスクに置かないためです。再起動で消えます。取ってから 24 時間でも消えます（戻ってこないアカウントの分が、全アカウントで共有の合計を埋め続け、誰にも消せなくなるのを防ぐため）。必要になったら、ディスク保存を別の選択として足します。
- **PostgreSQL の実時間ストリーム**: `pg_stat_statements` は集計された正規化済みの文で、1 回ごとの実行の時系列ではなく、有効化には `shared_preload_libraries` と再起動が要ります（tsmyadmin は Docker へ GET しか発行しないので、代わりに有効化できない）。そのため、回数の増加を読み取りの間隔ごとに示す形にし、使えないときは Docker での有効化の手順を出します。

## 次の候補（未実装）

導入と日々のトラブル対応を楽にするものを、効果が大きい順に並べます。

1. **アプリからつなぐ接続情報のコピー**: 検出したコンテナごとに、ホストから見たアドレスと別コンテナから見たアドレス（`host.docker.internal` か compose のサービス名）、`DATABASE_URL` 形式、`.env` の行を出す。
2. **ロック待ちと接続過多の可視化**: 「どのクエリが誰を待たせているか」を 1 画面で見せ、待たせている側をワンクリックで終了できるようにする（MySQL は `performance_schema`、PostgreSQL は `pg_locks`）。
3. **コンテナの起動を待つ**: 後から起動したコンテナが、ログイン画面を開き直さなくても出て、起動中（未準備）が分かる。
4. **スナップショットとスキーマ差分**: マイグレーションの前後で「何が変わったか」を DDL で示す。

## 既知の限界

- **初期 JS の予算**: 170 kB のうち約 160 kB を使っています（`bun run size`）。160 kB で 159.9 kB に達したとき、削らずに 170 kB へ上げました。内訳（初期 JS、minify 後）は、react-dom 33%、zod 17%、日本語の文言 13%、TanStack Router / Query 約 18%、共有スキーマ約 7%。**zod は初回表示から外せません**（ルート定義の検索パラメータの検証と、`readPreference` が zod のスキーマを受け取る設計が、初回表示の経路にあるため）。効くのは文言だけで、画面ごとに文言を読み込めば最大で約 20 kB 減らせますが、`locale.` を読む 208 ファイル（うち 53 か所はモジュールの先頭でセクションを取っている）に触れ、取り損ねは型ではなく、その画面を開いた実行時に `undefined` で見つかります。この規模では割に合わないので、次に予算を超えたときに、これを出発点に検討してください。
- **PostgreSQL の実物テスト**: テスト用の compose には `pg_stat_statements` が入っていないため、「実行された文」の PostgreSQL の経路は、拡張を入れた一時コンテナでだけ確認しています。CI に載せるには、compose の起動コマンドと fixtures の変更（と `db:reset`）が要ります。
- **起動中が分かるのは、ヘルスチェックのあるコンテナだけ**です。ヘルスチェックのないコンテナは、DB がまだ接続を受け付けていなくても、起動した時点で一覧に出ます（Docker の公開ポートは、中のプロセスが待ち受ける前から接続を受け付けるため、TCP の到達では見分けられません）。そのあいだのログインは、接続の失敗になります。
- **MySQL の「自分の文を除く」は接続単位**です。同じサーバーに別の tsmyadmin セッションがあると、そちらの文はアプリの通信として出ます。

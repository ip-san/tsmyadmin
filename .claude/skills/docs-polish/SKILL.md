# Docs Polish Skill

README.md / docs/*.md の**構成と文章だけ**を自然にする。事実（バージョン・ポート・環境変数名・コマンド・アンカー付きリンク）は一字も変えない。

## 対象ファイルの決め方

1. 引数でパスが指定されていればそれを使う
2. 指定がなければ **README.md** を既定にする（Slack や社内共有の入口になるため）
3. `git status --short` と直近のスクラッチパッドを見て、すでに下書きが無いか確認してから始める

## 手順

### 1. 元ファイルと「唯一の正」を読む

対象ファイルだけでなく、そこに書かれている主張の裏付けとなるドキュメントを必ず開く（例: 環境変数は `docs/deployment.md`、開発向け機能の挙動の詳細は `docs/dev-environment.md`）。技術的な主張は記憶やパラフレーズで書かず、原典と照合する。

`CLAUDE.md` の Compact Instructions（特に英訳義務・`docs:sync`）を確認する。

### 2. 書く前に advisor に方向性を確認する

対象ファイルを確定させたうえで、「事実は変えない、構成と文章だけ整える」という方針を明示して相談する。ここで良い助言が返ってくる（AI っぽさの具体的な構造上の問題点、扱う優先順位）。

### 3. AI っぽさは語彙ではなく構造で狙う

チェックすべき具体的パターン:

- 入れ子の括弧、文中の**太字**の乱用、説明的なダッシュ（—）
- 同じ注意書き・同じリンクを3行以内で2回言っている（自己剽窃）
- 「特にありません」と言いながら実装済み機能を説明している矛盾した節
- 同じ検査スクリプトなどの二重掲載（コピペ跡）
- 利用者向けの機能一覧に、開発者向けの内部構成（モノレポ構成など）が混ざっている

### 4. 事実を変えずに書き直す

バージョン番号・ポート・環境変数名・コマンド・アンカー付きリンクは一字も変えない。技術的な主張を言い換えるときは、必ず手順1で開いた出典ドキュメントと1文ずつ突き合わせる（次の「事実ドリフト」参照）。

### 5. 英語ファイルを同じ構成で追随させる

`CLAUDE.md` により、`docs/*.md` や `README.md` を変えたら `docs/en/` または `README.en.md` も更新し、`bun run docs:sync` を実行するのが必須。見出しを大きく変えたときは英語側も同じ見出し構成にする（逐語訳ではなく、自然な英語で書き直す）。

### 6. 機械チェックを実行し、実際の出力を確認する

```bash
bun run docs:sync
bun run docs:i18n
bun run docs:validate
```

これらは「翻訳ハッシュの一致」と「`CLAUDE.md` の統計値の一致」しか見ない。**文章の矛盾や繰り返しは検出しない**という前提で次に進む。

### 7. 機械チェックが見ない2点を手動で確認する

- **事実ドリフト**: 書き直した技術的な主張を、出典ドキュメントと1文ずつ再照合する。「両方言で同じ」のように一般化した記述は、方言ごとの違いを消していないか要注意
- **見出し変更によるアンカーリンク破損**: 見出しを変えた・消した・移動した場合、他ファイルからの `ファイル名#見出し` リンクが壊れていないか確認する

```bash
grep -rn '対象ファイル名\.md#' docs CLAUDE.md CHANGELOG.md .claude apps packages e2e 2>/dev/null
```

### 8. 書き直した後、もう一度 advisor に見せる

1回目（方向性確認）と2回目（機械チェック通過後）は別の役割。2回目は「緑のチェックの裏で残っている矛盾・繰り返し」を探すためのもの。**この2回目が本当に効く**（後述の失敗例を参照）。

### 9. 指摘を直し、`docs:sync` / `docs:i18n` / `docs:validate` を再実行する

### 10. 報告する

- ユーザーはツール出力を直接見ない。実行した検査コマンドの**実際の結果**（PASS/FAIL の文言）を最終メッセージに書く
- Slack 投稿が目的のときは、3行程度のそのまま貼れる紹介文を最終メッセージの中に書く（リポジトリには入れない）
- コミット・push は明示的な指示があるときだけ行う。指示がなければ「コミットしていません」と明記する

## このプロジェクトで実際に起きた失敗（教訓）

| 失敗 | 原因 | 対策 |
|---|---|---|
| PostgreSQL の「実行された文」を MySQL と同じ「リアルタイム」と書いた | トーンを整える言い換えが、方言ごとの違いという事実を消した | 手順7の事実ドリフト確認を、機械チェックの後に必ず入れる |
| 「接続先を書く必要がない」を3箇所近くで繰り返した | 構成を組み替える途中で同じ内容を別の場所にも書いた | 手順8で advisor に通し読みさせ、繰り返しを検出する |
| 機械チェックが緑だったので安心して終わりにしかけた | `docs:sync`/`docs:i18n`/`docs:validate` は翻訳の同期としか見ておらず、文章の整合性は見ない | 緑 = 完了ではない。手順7・8を機械チェックの代わりにしない |

## 参考: pre-push ゲートの構成

`check:static` = `check`（型・lint・ユニット/API/Web テスト・type-coverage）+ `check:quality`（knip・循環依存・cpd・arch・sql-safety・`docs:validate`・`docs:i18n`・contrast）。ドキュメントだけの変更でも `git push` はこの全体を通る。
